# 决策模型微调全流程 · 实操手册


## 0. 一句话概括

把「状态 + 明确问题 + 候选答案」变成「带标定概率的答案」，用**判别式**训练（不生成任何文本）。

```
聊天模型:   文本 ──► 文本                （要解析、拿不到置信度）
决策模型:   state+questions ──► 概率分布  （结构化、置信度可用、可校准）
```

---

## 1. 全景

```
① 数据   Open-Jev JSONL ──► 转 typed 格式 ──► 裁决「拆/不拆」──► parquet
         V3: 11 个 source 原生多问题整条保留；只把 painting 138 个
             超长 case 拆成单问题并分层抽 5%（1,177 条）
                                                  │
② 环境   torch 2.13.0+cu130 / unsloth 2026.11.2 / transformers 5.17.0 /
         trl 1.15.0 / tokenizers 0.23.3（云端 A10）
                                                  │
③ 训练   FastDecisionModel.from_pretrained(4B, NF4 4bit, max_seq=4500)
         └─ get_peft_model(r=16)  →  决策头 + LoRA 一起训（64.5M / 3.07B = 2.10%）
         └─ DecisionTrainer      →  soft CE + Brier，400 步 / 有效 batch 16
                                                  │
④ 标定   在 calibration 集拟合温度（choice/score/noul 各一个）
                                                  │
⑤ 评测   test / ood 全量、只跑一次；训练/评测/推理全部「一次直出」
                                                  │
⑥ 保存   adapter/ = LoRA + 决策头 + 温度配置
                                                  │
⑦ 推理   state + 多个 questions ──► 一次前向 ──► 校准概率
```

## 2. 数据准备

### 2.1 为什么要"转换"

Open-Jev 原始格式是**每行一个问题**（79,116 行 / 7,256 group）。
Unsloth 的 `build_dataset` 吃 typed-decisions 格式：一行 = 一个 state + 一组 questions + gold。

两者由官方 `jev/api.py` 的 `compile_request` / `format_response` 定义（同一套 schema），
所以转换是无损的。脚本：`jev_prep/to_typed_decisions.py`。

### 2.2 V3 的核心裁决：哪些绝对不能拆

**共享编码**范式下，一个 case 的所有问题 + 候选描述编成**一条序列**。序列太长怎么办，
不能只看长度，必须**逐条读 `instructions` 原文**判断问题之间有没有联合约束。

| 裁决 | source | 依据 |
|---|---|---|
| **不能拆** | 4 个 `workflow-controls` | 原文写着 `Exactly one final disposition is selected` / `The output is an action set, potentially empty` / `respect the workflow action cardinality` —— 多个问题是一次互斥决策，拆开就丢约束 |
| 可以不拆 | `customer-control` / `reasoning-control` / `snake` / `vizdoom` | ≤1,128 token，无联合约束 |
| 本来就 N=1 | `tic_tac_toe` / `tile_platformer` / `trex_runner` | 数据天生一个 state 一个问题 |
| **可以拆** | 只有 `painting-geometry-v1` | 每题自包含、state 含完整画面、无联合约束；但一条 20k–60k token |

**V3 解法**：把 `max_seq` 从 1024 提到 **4500** —— 实测最长的
`security_incidents` 是 4,396 token，4500 刚好让 **11 个 source 全部整条保留**，
于是**只有 painting 的 138 个 train case 需要处理**：拆成 23,552 个单问题片段后
按 `(case 尺寸, label)` 分层抽 **5% = 1,177 条**，避免它独占一半训练算力。

`max_seq=4500` 全库长度实测：p50 578 / p90 2,208 / p99 4,390 / max 60,212；
超长样本 **100% 来自 painting**（train 138 / calib 3 / valid 3 / test 18 / ood 18）。

逐条审查的证据：`jev/results/split_legality.md`；生成脚本 `jev/scripts/make_hybrid_v3.py`。

### 2.3 拆分的安全阀：group_id

**同一原始 case 的所有问题必须留在同一 split**，否则测试集状态在训练里出现过。
Open-Jev 官方已保证 group 不跨 split → 拆分时原样保留 `group_id`。

实测拆分前后 group 数完全一致：
train 7,256 / calib 468 / valid 452 / test 893 / ood 1,402。

### 2.4 校验方法（别信"看着对"）

用 **unsloth 自己的** `_target_for` 逐条解析我们造的数据，比对目标分布与原始标签。

V3 全量校验（`jev/scripts/verify_v3.py`）：

```
跨 split 的 group_id 交集 → 空（无泄漏）
5 个切分 build_dataset    → 全部 skipped 0
全量编码最长              → 4,400 token ≤ 4500，超长 0 条
decision_config max_len   → 4500
```

V3 五个切分（case / 题数）：train 15,580 / 55,523，calibration 1,078 / 4,086，
validation 932 / 3,145，test 1,902 / 7,136，ood 1,772 / 8,627。
完整盘点见 `jev/results/v3_inventory.md`。

### 2.5 两个数据格式坑

1. **pandas 写的 parquet 带 pandas metadata**，`datasets` 读时提示
   `column names don't match` 并触发缓存重建 → 用 **pyarrow 直写**。
2. **扁平列别留**。`<qid>__label` 之类有 972 个（各 case 问题名的并集），大多是 NaN，
   还会让 schema 校验出问题 → 只留 6 列：
   `state / questions / gold / group_id / source / n_questions`

体积：972 列 7.7 MB → 6 列 **1.05 MB**（zip 后 0.9 MB）。

## 4. 训练

### 4.1 三个 API 的分工

```python
from unsloth import FastDecisionModel, DecisionTrainer, is_bfloat16_supported

model, tokenizer = FastDecisionModel.from_pretrained(
    model_name=..., max_seq_length=4500, load_in_4bit=True)
model = FastDecisionModel.get_peft_model(
    model, r=16, lora_alpha=16, lora_dropout=0,
    use_gradient_checkpointing="unsloth", random_state=3407)
items, report = FastDecisionModel.build_dataset(dataset, tokenizer, model)
trainer = DecisionTrainer(model=..., train_dataset=items,
                          eval_dataset=valid_items, args=...)
```

**注意**：是 `DecisionTrainer`，**不是 `SFTTrainer`**。用 SFTTrainer 会丢掉概率语义。

> 关于 `FastDecisionModel` 里那个决策头长什么样、"输出头"和"头网络本体"有什么区别，见 **附录 B**。

### 4.2 步数怎么算

```
1 step = 1 次参数更新 = bs × accum 个样本

V3:  400 步 × (2 × 8) = 6,400 个 case = 15,580 的 41.1%
     全量一遍 = 15,580 ÷ 16 = 974 步（V3 只跑了 0.41 epoch）

v2:  200 步 × (8 × 4) = 6,400 个 case = 77,898 的 8.2%
```

⚠️ `--steps` 会**覆盖** `--epochs`：脚本默认值是 `epochs=2`，但显式传
`--steps 400` 后按步数停，所以 V3 是 `epoch=0.4108`，不是 2 epoch。

**更新次数**决定收敛，不是样本总数。同样 6,400 个样本：1 个大批量 = 1 次更新（泛化差），400 个小批 = 400 次更新（好）。注意两轮虽然都是 6,400 个样本，但 V3 是**原生多问题整条**，v2 是**单问题行**，不可比。

### 4.3 何时停

| 现象 | 动作 |
|---|---|
| acc 涨、loss 降 | 继续 |
| acc 涨、loss 平 | 继续（loss 含校准项） |
| acc 平、loss 平 | 收敛，停 |
| acc 掉、loss 涨 | 过拟合，停，用最好的 checkpoint |

## 5. 标定（这套范式的灵魂）

### 5.1 为什么必须有

softmax 出来的概率 ≠ 真实正确率。模型说"90% 确定"的那批，可能只有 70% 对。

### 5.2 温度是什么

```
P = softmax(logits / T)
T > 1 → 概率更保守
T < 1 → 概率更自信
```

一个标量就能把整条概率曲线调到接近真实频率。

### 5.3 实测：三种题型各一个温度

V3 实测（`model/adapter_v3/unsloth_decision_config.json`）：

```json
"max_len": 4500,
"temperature": [1.0180, 0.7108, 1.0195]   // choice / score / noul
"folded_temperature": 1.0257
```

| 题型 | T | 含义 |
|---|---:|---|
| choice | 1.02 | 几乎不用调 |
| **score** | **0.71** | 过度保守 → 放开 |
| noul | 1.02 | 几乎不用调 |

日志里的 `fitted_types=[0,1,2]` 是**成功拟合温度的题型编号**，不是温度值
（`_metrics` 返回 `accuracy / ece / loss / record_accuracy`，`calibrate` 另加
`fitted_types = sorted(fitted)`）。

（v2 历史值：`[1.3386, 0.5, 1.2191]`，`folded=1.0544`。两轮数据形态不同，不可比。）

> ⚠️ **数组顺序是 `("choice","score","noul")`**（`_decision_common.py:58`），
> **不是** `choice/noul/score`。Clef head 内部另有 `{"noul":0,"choice":1,"score":2}`，
> 两套编号在 `decision.py:445-446` 显式映射。别搞混。

**效果（V3）**：`ece` 从 0.0253（step 400 validation，未标定）→
**0.0134（test）/ 0.0161（ood）** 标定后。
官方 Open-Jev 只用**单一**标量温度（1.5188）→ 分题型更细。

### 5.4 铁律

温度**只能在 calibration 集上拟合**，冻结后才能用于 test/ood。
用 test 调温度 = 拿答案调旋钮，报出来的分数是假的。

## 6. 评测

### 6.1 五个切分的职责

| 切分 | 职责 | 时机 |
|---|---|---|
| train | 更新权重 | 训练时 |
| **validation** | 监控收敛、选 checkpoint | 训练中每 N 步 |
| **calibration** | **只**拟合温度 | 训练结束后一次 |
| test | 最终报告 | **只跑一次** |
| ood | 泛化报告 | **只跑一次** |

### 6.2 四个指标

| 指标 | 含义 | **V3 test** | V3 ood |
|---|---|---:|---:|
| accuracy | argmax 命中率（逐题） | **0.8960** | 0.9220 |
| **ece** | 置信度与真实频率的偏差 | **0.0134** | 0.0161 |
| loss | 交叉熵（含标定项） | 0.2265 | 0.2132 |
| **record_accuracy** | **一个 case 的所有问题全对才算对** | **0.6593** | 0.6919 |

⚠️ V3 是**原生多问题整条评测**，所以 `record_accuracy` 天然低于逐题 accuracy；
v2 全拆版每行只有 1 题，两者相等（都是 0.9766）。**这两个数字口径不同，不能比。**

**只看 accuracy 会掩盖问题**：acc 80% 但 ECE 0.3 的模型没法设阈值。
本项目最该看的其实是 `record_accuracy`，它直接对应「一次直出整条全对」的能力：
baseline 0.1062 → step400 0.6470 → test 0.6593。

**「不设验收阈值」**：这是个人项目，用于简历，不设 pass/fail 门槛；
所有数字如实报告，口径与排除量全部写明。

## 7. 保存与加载

### 7.1 adapter 目录里有什么

V3 本地实际目录 `jev/model/adapter_v3/`（10 文件 / 214.1 MB）：

```
adapter_model.safetensors     129.9 MB  LoRA r=16（32.46M 参数）
joint_head.safetensors        64.1 MB  决策头（32.05M 参数，fp32）
joint_head_config.json                 {hidden_size:2560, width:512, routing_layers:2,
                                        layers:4, heads:8, feedforward:2048}
unsloth_decision_config.json            {"layout":"clef","max_len":4500,
                                        "temperature":[1.0180,0.7108,1.0195],
                                        "folded_temperature":1.0257, ...}
adapter_config.json                     PEFT 配置
tokenizer.json / tokenizer_config.json  20 MB
```

底座冻结（NF4 4-bit），真正训练的只有 LoRA + 决策头 = 64.51M / 3.07B = **2.10%**。

### 7.2 跨机器搬移必须改路径

```json
// adapter_config.json
"base_model_name_or_path": "/mnt/workspace/models/Qwen3.5-4B"
// unsloth_decision_config.json
"base_model": "/mnt/workspace/models/Qwen3.5-4B"
```

不改 → 本地加载去找 `/mnt/workspace/...` 而失败。

### 7.3 加载

```python
model, tokenizer = FastDecisionModel.from_pretrained(
    model_name=r"model/adapter_v3",
    max_seq_length=4500, load_in_4bit=True)   # ← 4500 必须显式传
answers = FastDecisionModel.predict(model, tokenizer, state, questions)
```

温度会自动从 `unsloth_decision_config.json` 读回。

> ⚠️ **本地重载的坑（已实测）**：配置文件里写的是 `max_len=4500`，
> 但 `_load_clef` 里 `max_len = int(max_seq_length or CLEF_MAX_LEN)`，
> `config.update(..., max_len=max_len)` 会**无条件覆盖**保存的值。
> 不传 `max_seq_length` 就会被降回 **4096**。
>
> 影响：V3 里编码长度落在 4096–4500 的样本
> train 522 / calib 57 / valid 18 / **test 78 / ood 75** 条会被截断。
> `predict` 走 `CLEF_SERVE_MAX_LEN=16384`，推理不受影响；
> 但用 `build_dataset` / `evaluate` 复现评测时数字会对不上云端。
>
> 显式传 4500 后实测：`test 全量 build_dataset: 1902 items, skipped 0/7136`。

## 附录 A：v2 历史 breakdown（**已废弃口径，勿用于 V3 结论**）

### B.1 "头（head）"这个词

深度学习里模型分两截：

```
backbone（主干）  →  负责"理解"，输出一串 hidden states
head（头）        →  负责"把理解变成答案"
```

类比：读完一封邮件（backbone）→ 脑子里有理解 → 拿笔答题（head）。笔就是头。

- 聊天模型的头：把理解变成"下一个字" → 逐字生成文本
- 判别式决策模型的头：把理解变成"每个候选得几分" → 输出一组数字

头通常很小：本轮底座 3.07B，头 32.05M。

### B.2 两个容易混的概念

```
┌──────────────────────────────────────────────┐
│  Qwen3.5-4B 底座（3.07B，冻结 + LoRA 微调）      │
│  输出：序列里每个 token 一个 2560 维向量          │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│  ① 决策头网络本体 = 一台加工机器（32.05M 参数）    │
│     投影 → 注意力 → 打分，一套，所有题型共用        │
└──────────────────────────────────────────────┘
                    │ 每个候选 1 个未归一化分数（logit）
                    ▼
┌──────────────────────────────────────────────┐
│  ② 题型通道 = 三套"读分数"的规则（几乎无参数）      │
│     choice / noul / score                     │
│     + softmax + 温度标定（都在 head 之外）        │
└──────────────────────────────────────────────┘
                    │
                    ▼
        { answer, probabilities, confidence }
```

**① 是实体（有 3200 万参数）；② 更像说明书（告诉我们怎么翻译分数）。**

### B.3 ① 决策头网络本体：三步

用本轮实际跑过的工单走一遍：

```
state: 客户反馈：订单被重复扣款两次，已经等了三天，要求立刻退款，否则就投诉。

route     (choice)  候选：billing / technical / account / other
urgency   (score)   候选：0 可以排队 / 1 优先 / 2 立即人工介入
refund    (noul)    候选：true / false
```

底座读完序列后，每个 token 得到 2560 维向量。头接手：

#### 第 1 步：压成 512 维，但从 6 个角度看

配置 `hidden_size=2560` / `width=512` → 6 个 `Linear(2560, 512)` 投影：

| 投影 | 输入 | 得到什么 |
|---|---|---|
| `memory_projection` | 全部 token | **记忆库**（后面反复回看） |
| `question_projection` | 每个问题 span 的 mean pooled | 问题的"意思" |
| `global_projection` | 序列最后一个 token | 整条信息的"总印象" |
| `option_context_projection` | 选项 span 的 mean pooled | 选项在文中的上下文 |
| `option_lexical_projection` | 选项 token 的 LM 输出 embedding 均值 | 选项**字面上**是什么 |
| `option_question_projection` | 问题向量广播给它的每个选项 | 该选项配这道问题 |

> 为什么要投 6 次？"billing 这个词本身"（lexical）、"billing 出现在这句话里"（context）、
> "billing 配'该交给谁'这个问题"（question）是三件不同的事，机器要分开表示。

#### 第 2 步：让选项和问题"互相看"

```
evidence_layers（routing_layers=2）：每个选项去全序列里"找证据"（cross-attn + FFN）
layers（layers=4）：4 层 TransformerDecoder，问题字段间交流 + 回看记忆库
```

**`heads=8` 是这两处 MultiheadAttention 的"观察视角"数**（512÷8=64 维/视角），
**不是输出头数，与三种题型无关** —— 这是最容易混淆的地方。
`feedforward=2048` 是每层 FFN 的中间宽度。

#### 第 3 步：给每个候选打一个分

```
logit = 词面先验 + 门控 × ( 联合余弦相似度 + 残差打分 )

logit = exp(prior_logit_scale) · prior_cos
      + sigmoid(residual_gate) · ( exp(joint_logit_scale) · cos(field, option)
                                  + residual_scorer([field, option,
                                     field*option, |field-option|]) )
```

| 项 | 含义 |
|---|---|
| `prior_cos` | 选项字面与「问题+全局」的余弦相似度 → 不学也知道 billing 和退款相关 |
| `cos(field, option)` | 网络学出来的"这个 field 和这个 option 有多配" |
| `residual_scorer` | 共享 2 层 MLP `2048→512→1`，看 4 组组合特征打补丁 |
| 3 个标量参数 | `prior_logit_scale` / `joint_logit_scale` / `residual_gate`，控制三项占比 |

**关键：这一步对 choice / noul / score 完全一样**，每个候选只输出 1 个数字。例如 `route` 得到 `[3.1, -0.8, -1.2, -2.0]` —— 尚未归一化。

### B.4 ② 那"3 个"到底是什么 —— 不是三个独立输出层

**三种题型共用一套网络、一个共享的 1-logit-per-option 打分器**，区别只有 4 处：

| 区别 | 位置 | 说明 |
|---|---|---|
| **候选集合不同** | 数据层 | choice 用 `criteria` 的键、noul 固定 `true/false`、score 用等级下标 |
| **`type_embedding`** | 头内，**仅 1536 参数** | `Embedding(3, 512)`，题型编号 `{noul:0, choice:1, score:2}`，加性条件加到 question field |
| **softmax + 温度** | **头外** | 全体候选 softmax；温度按题型分三档 |
| **读答案的方式** | **头外** | 见下表 |

读答案的规则：

| 题型 | 分数怎么变成答案 |
|---|---|
| `choice` | 全体 softmax → argmax = `billing`，confidence = 最大概率 |
| `noul` | 取 `probabilities["true"]` = P(为真) |
| `score` | 算**期望档位** `Σ 档位 × 概率`（如 1.97，最可能是 2） |

训练时还有一处差异：**只有 score 多一项 ordinal partial credit 损失** —— 把
"选错档位离正确档位多远"也算进去，因为把"立即介入"错判成"可以排队"，
比错判成"优先"更严重。noul / choice 都是普通 soft CE。

> **准确说法：1 个共享的决策头网络 + 3 种题型通道（解读规则）。**
> 口语说"3 个输出头"会让人误以为三套独立参数，不严谨。
> 实测佐证：`type_embedding` 张量恰好 `3 × 512 = 1,536` 个参数；
> `joint_head.safetensors` 里**没有** `choice_head` / `noul_head` / `score_head` 这类张量。

### B.5 参数账（与训练日志完全吻合）

```

  layers                  16,816,128   4 层 TransformerDecoder
  evidence_layers          6,306,816   2 层证据路由

  residual_scorer          1,049,601   2 层 MLP

```

### B.6 为什么值得用这么复杂的一个头

| 方案 | 做法 | 判 3 件事要几次底座前向 |
|---|---|---|
| 官方 Open-Jev 标量头 | `Linear(2560,1)`，每候选独立跑 | 4+3+2 = **9 次** |
| 桌面 0.8B query/key 头 | 262,400 参数，极轻量 | 少，但能力有限 |
| **Unsloth joint-schema** | 一次前向，**所有问题 × 所有候选一起处理** | **1 次**                |

名字里的 **joint（联合）** 就是这个意思：不是给每个选项单独打分，
而是把整张"问题 × 选项"表一起送进小 transformer，让选项之间、问题之间互相参照。

代价 32M 参数（比标量头大 100 倍），换来 **9 倍速度** 与"能看见全局"的能力。

### B.7 一句话记住

> 底座读进去；头把"读懂的东西"压成 512 维、让选项互相参照、
> 给每个候选打一个分 —— 这一整套是**一个 32M 参数的网络（①）**。
>
> 分数出来后，"选择题取最大、noul 读成立概率 p、打分题算期望" ——
> 这三套是**解读规则（②）**，几乎没有参数。
>
> `heads=8` 是注意力视角，与题型无关；三个题型只靠一个 1536 参数的
> `type_embedding` 区分。

### C.3 spans：head 靠「坐标」取向量

`encode_record` 除了生成 token 序列，还记下每个问题/选项在序列里的起止位置：

```text
route              question_span=[82, 91]  option_spans=[[102, 117], [123, 138], [144, 155], [161, 176]]  options=['account', 'billing', 'other', 'technical']
urgency            question_span=[197, 204]  option_spans=[[215, 228], [234, 246], [252, 265]]  options=['0', '1', '2']
refund_requested   question_span=[288, 295]  option_spans=[[306, 324], [330, 348]]  options=['true', 'false']
```

所以 head **不是**去解析模型输出的文字，而是拿着这些坐标到 `hidden_states` 里切片。
这也是它结构上不会幻觉、不会格式错乱的原因。

### C.9 一眼看懂的四个观察

1. **模型一个字都没生成**。整条链是「读 370 token → 取 span → 打分 → softmax」。
2. **9 个候选共享一次前向**，不是 9 次；对比官方标量头要跑 9 次底座。
3. **`type_embedding` 只有 `[1,3,512]`** —— 三种题型靠 1536 个参数区分，没有三套独立输出层。
4. **温度在 head 之外**，是标定阶段学来的三个标量；head 本身只吐未归一化的 logit。

### D.0 一个画面贯穿全部：这是一张 Excel 表

```
一张表：370 行 × 2560 列

        列1      列2      列3    ...   列2560
行0   -0.018   0.005   0.019  ...  -0.001    <- token "<|im_start|>"

```

**每一行 = 一个 token，每一列 = 一个数字。整张表 = 370 × 2560 = 947,200 个浮点数。**
后面所有「取向量」「压成 512 维」「开会」「打分」，都是对这张表做行/列运算。

### D.1 「2560 维向量」长什么样？是 embedding 模型吗？

**从底座权重里真实读出来的一行**：

```text
model.language_model.embed_tokens.weight : [248320, 2560]
token id 8678 = 'system' 的向量，前 16 个数：
[-0.018066, 0.005493, 0.019409, -0.005524, 0.001793, 0.002014,
  0.009399, -0.006042, -0.005371, 0.016479, -0.010986, -0.001808,
  0.003967, -0.006622, 0.010925, 0.003937]
长度 2560 | min -0.0400 | max 0.0498 | 均值 0.0000 | L2 范数 0.6324
```

**「2560 维向量」就是 2560 个小数排成一行，没有别的玄学。**
2560 来自 Qwen3.5-4B 架构的 `hidden_size`，不是我们选的。

是不是 embedding 模型？**一半对，一半不对**：

| | 说明 |
|---|---|
| ✅ 对 | 起点确实是查表：tokenizer 切成 id → 查 `[248320, 2560]` 的词嵌入表，一个 id 换一行 |
| ❌ 不对 | 底座 28 层 Transformer 会把这 370 行**反复改写**，输出的是「这个词在这句话里的意思」，不再是字典义 |
| ❌ 不对 | embedding 模型通常输出**一个**句子向量；这里输出 **370 行**（每个位置一行），因为 head 要靠位置取 |

例：同一个「苹果」在「吃苹果」和「苹果发新机」里查表得到同一行，但底座读完句子后输出两行不同的数字。

### D.2 底座像 BERT 还是 GPT？带因果掩码吗？

**分两层答，答案不一样。**

| 层 | 类型 | 掩码 |
|---|---|---|
| **底座 Qwen3.5** | GPT 式（decoder-only，自回归） | **有因果掩码**，位置 i 只能看 0..i |
| **head** | 更像 BERT（双向） | **无掩码**，3 个 field / 9 个 option 互相可看 |

底座这次是 **prefill（预填充）**，370 token 一次喂入，不生成下一个字。因果掩码的实际效果：

```text
底座算第 130 行（billing 那段）时，只能看到第 0～129 行
  -> 能看到前面的 state（重复扣款、退款）  OK
  -> 看不到后面的 FIELD 2 urgency / FIELD 3 refund  NO
```

但 **head 是在底座把整条 370 行读完之后才工作的**，拿到的 `memory` 是全序列成品；
且 head 内部的「序列」是 3 道问题 / 9 个选项，**不是时间步，没有过去/未来**。
所以 9 个选项互相看得见、3 道题互相看得见、都能回看全部 370 行。

> 一句话：底座「从左往右读」，head「读完后把整张摊开的表交叉比对」。

### D.3 「按 span 取向量 → 6 路投影压到 512 维」

#### ① span = 圈出几行

`billing` 选项的 span = `[123, 138]`，共 **15 行**，逐 token 真实内容：

```text
{"  description  ":"  账单  、  发票  、  退款  相关  ","  option  _id  ":"  billing  "}
```

「取向量」= 从 370 行表里圈出这 15 行 → 得到 `15 × 2560` 的小表。

#### ② 池化 = 按列求平均，压成 1 行

```text
15 × 2560  ->  每一列求平均  ->  1 × 2560
```

一个选项用了 15 个 token 描述，但 head 只要一个向量代表它。

#### ③ 投影 = 乘一个矩阵

从 `joint_head.safetensors` 读出的 6 个矩阵，**每一个都是 `[512, 2560]`**：

| 矩阵 | shape | 参数量 | 前 4 个权重（实测） |
|---|---|---:|---|
| `memory_projection` | `[512, 2560]` | 1,310,720 | [0.0105, 0.00928, -0.013, 0.01392] |
| `question_projection` | `[512, 2560]` | 1,310,720 | [-0.0144, -0.00013, 0.00522, -0.01318] |
| `option_question_projection` | `[512, 2560]` | 1,310,720 | [-0.0188, -0.01117, 0.00589, -0.00729] |
| `global_projection` | `[512, 2560]` | 1,310,720 | [0.00952, -0.00562, 0.00074, -0.01221] |
| `option_context_projection` | `[512, 2560]` | 1,310,720 | [-0.00061, -0.00241, -0.01782, -0.00867] |
| `option_lexical_projection` | `[512, 2560]` | 1,310,720 | [0.00879, 0.01044, 0.00946, 0.01868] |

```text
[1 × 2560]  ×  [2560 × 512]  =  [1 × 512]
第 j 个输出 = 2560 个输入 × 该矩阵第 j 列的 2560 个权重，再加起来
```

**类比**：2560 项体检指标，用一张 512 行的问卷重新打分，每题是若干指标的加权和，权重训练学出来。
不是删信息，是换一套更紧凑的说法。

#### ④ 6 路 = 同一个 2560 行，乘 6 个不同矩阵

| 矩阵 | 拿哪几行平均 | 想表达 |
|---|---|---|
| `question_projection` | 问题那几行 | 这道题在问什么 |
| `global_projection` | 最后一行 | 整条信息的总印象 |
| `memory_projection` | **全部 370 行**（不平均） | 全文资料库 |
| `option_context_projection` | 每个选项那几行 | 选项在文中的上下文 |
| `option_lexical_projection` | 选项的词表向量 | 选项字面是什么 |
| `option_question_projection` | 复用问题向量，广播给它每个选项 | 该选项配这道题 |

真实激活值（hook 抓的，`billing` 位于 9 个选项的第 1 位）：

option_lexical_projection      [1, 9, 512]  billing 位置前 4 个数 = [-0.00504, -0.0, -0.00528, -0.00354]

### D.4 「2 层证据路由 + 4 层 Transformer」是哪儿来的

**不是我们选的，是架构自带的**，写在 `joint_head_config.json`：

```json
{"hidden_size": 2560, "width": 512, "n_types": 3, "routing_layers": 2, "layers": 4, "option_projections": ["memory_projection", "question_projection", "option_question_projection", "global_projection", "option_context_projection", "option_lexical_projection"]}
```

`from_pretrained` 读配置后照着搭 `ModuleList`：2 个 `EvidenceRoutingLayer` + 4 个 `TransformerDecoderLayer`。
类比：LoRA 的 `r=16` 是我们选的；head 层数是模型「出厂」定好的。

| 层 | 输入 → 输出 | 干什么 |
|---|---|---|
| `evidence_layers` ×2 | `[1,9,512]` → `[1,9,512]` | 9 个选项各自当查询，去 `memory`（370 行 × 512 列）找证据，带回来修正自己；连做 2 轮 |
| `layers` ×4 | `[1,3,512]` → `[1,3,512]` | 3 个 field 之间 self-attn + 回看 memory 的 cross-attn + FFN；连做 4 轮 |

**类比**：2 轮「9 个调查员各去档案室翻资料」，4 轮「3 个评委开会互相看判断再回全文核对」。

真实数值变化（同一位置，形状不变、数字被改写 —— 这就是「层」的全部含义）：

```text
layers.0     输出前 4 个数 = [-0.73449, -2.55827, 0.22018, 0.04934]
layers.3     输出前 4 个数 = [0.54798, -1.45268, 1.49483, 0.80983]
```

### D.5 「3 个 field 开会」= 3 类题型互看吗？**不是**

⚠️ **最容易误解的一处**。附录 B/C 的例子里**恰好 3 道题、恰好 3 种题型**，两个「3」撞在一起纯属巧合。

**`[1, 3, 512]` 的 3 行 = 这一条记录里的 3 道具体问题**（route / urgency / refund_requested），
**不是** choice/score/noul 三类。源码 `build_layout`：

```python
q_max = max(len(r.questions) for r in records)   # 问题个数，不是题型种类数
```

**用 5 道题实测验证**（2 个 choice + 1 个 score + 2 个 noul，只跑 `encode_record`，不加载 4B）：

```text
5 个问题 -> encoded.questions 个数 = 5
题型分布 = [1, 1, 2, 0, 0]      (0=noul, 1=choice, 2=score)
选项总数 = 11
=> q_max = 5，field shape 是 [1, 5, 512]
```

**`type_embedding` 贴在每一行上，是「徽章」，不是「行」**：

> 3 个评委开会（3 个 field），每人胸前别一枚 `choice`/`score`/`noul` 徽章。
> 徽章告诉网络「这位该按什么规则给分」，但开会的是 **3 个人，不是 3 种徽章**。
> 换 5 道题就是 5 个评委，其中可能 2 人别同一枚徽章。

`self.type_embedding(type_ids)` 只是给第 i 行**加**一个 512 维向量，形状始终是 `[1, 问题数, 512]`。
题型只影响两件事：候选集合（4 个 / 3 档 / 2 个）和那枚徽章；**不影响有几行**。

### D.6 `noul` 是什么？为什么名字跟「是非」没关系

**词源：`noul` 来自 `Bernoulli`（伯努利）**。不是字典词、不是 boolean 缩写，
是 TypeSafe（Jev 作者）自创，从 Bernoulli 中间截字母拼成（类似 `influenza → flu`）。
来源：TypeSafe CEO Diogo Almeida 在访谈 / Hacker News 上说明；**官方文档未写**。

伯努利分布 `Bernoulli(p)` =「抛一次硬币，正面概率 p」，**全部信息由一个参数 `p` 决定**。
所以 `noul` 的设计不是「回答是或否」，而是 **输出这个命题成立的概率 `p`**。

这一下解释了所有「怪现象」：

| 现象 | 原因 |
|---|---|
| 返回只有 `{"type":"noul","noul":0.9849}` | 一个 `p` 就够，`P(false)=1-p` 是数学必然 |
| **没有 `probabilities`** | 伯努利分布不需要列概率表 |
| **没有 `confidence`** | 不是「从多个里选一个」，无所谓「选中的有多可信」 |
| `predict.py` 取 `confidence` 报 KeyError | 就是这个原因 |

三种题型其实是**三种不同的概率对象**：

| 题型 | 数学对象 | 返回 |
|---|---|---|
| `choice` | 多项分布（K 个互斥结果） | 选中项 + K 个概率 + confidence |
| `score` | 有序等级上的分布 | 各档概率 + 期望档位 + legend |
| **`noul`** | **`Bernoulli(p)`** | **一个 `p`** |

**两个该改口的习惯**：

1. 口语叫「是非题」不严谨，准确是「**命题成立概率**」。它不替你做决定，只给 `p`，阈值由 agent 定（`p>0.8` 才报警）。
2. **`p=0.5` 不是「中等」**，是「是和否各一半、模型完全没主意」。问「有多严重」用 `score`，`noul` 只能问「是不是」。

记忆法：**noul ≈ 一个 p 值，不是一对选项。**

### D.7 那「9 个选项」怎么来的？输入明明是 4+3+1

**`noul` 内部是 2 个候选，不是 1 个** —— 那两个候选是 API 自动补的。

你写的输入（没有 `criteria` 字段）：

```json
{"type": "noul", "instructions": "客户是否明确提出了退款请求？"}
```

`encode_record` 之后：

```text
route              type=1  候选=['account','billing','other','technical']  个数=4
urgency            type=2  候选=['0','1','2']                              个数=3
refund_requested   type=0  候选=['true','false']                            个数=2
                                                            合计 = 9
```

序列里真的写了两行（从 370 token 里切出的原文）：

```text
FIELD 3
ID: refund_requested
TYPE: noul
INSTRUCTION: 客户是否明确提出了退款请求？
ALLOWED OPTIONS:
OPTION 1: {"description":"The proposition is true or the answer is yes.","option_id":"true"}
OPTION 2: {"description":"The proposition is false or the answer is no.","option_id":"false"}
END FIELD
```

源码 `question_options()` 里写死：

```python
if str(question["type"]) == "noul":
    criteria = {"true": "The proposition is true or the answer is yes.",
               "false": "The proposition is false or the answer is no."}
```

**三层「数量」，别混一起**：

| 层面 | noul 是几个 | 为什么 |
|---|---:|---|
| 你写的输入 | **1 个问题** | 一句命题，没有候选要列举 |
| 内部计算 | **2 个候选** true/false | 做 softmax 至少要有 2 个分数；伯努利试验本就有成功/失败 |
| 返回给 agent | **1 个数 `p`** | `P(false)=1-p` 是数学必然 |

真实数字：

```text
refund/false  logit = -2.9192  ┐
refund/true   logit = +2.1773  ┘ 两个候选都参与 softmax
        / T=1.2191 -> softmax -> true 0.984941 / false 0.015059
        -> API 只留一个参数 -> {"type":"noul","noul":0.9849}
```

> 附带：`choice` 的候选走 `sorted(...)`，所以你写的 `billing,account,technical,other`
> 在内部变成 `account,billing,other,technical`（字母序）。这解释了 trace 里 `option_ids` 与输入顺序不同。

### D.8 「每项与每个 option 比余弦 + MLP 打补丁」

#### ① 不是 3×9，是 9 次比较

**每个选项只跟「它自己那道题」的 field 比**：

```text
route  的 4 个选项  <->  route  的 field
urgency 的 3 个选项 <->  urgency 的 field
refund 的 2 个选项  <->  refund  的 field
                          共 9 次比较
```

源码里 `repeated_field` 就是把 3 个 field 按各自选项数复制成 9 行（4 份 + 3 份 + 2 份）。

#### ② 余弦相似度

```text
cos(a, b) = (a·b) / (|a| × |b|)     值域 [-1, 1]
  +1 方向完全一致 -> 很配      0 垂直、无关      -1 方向相反 -> 不配
```

为什么不用点乘？点乘会被向量**长度**影响；余弦把长度除掉，结果锁在 [-1,1]，训练更稳。
（`field_norm` / `option_norm` 已做 LayerNorm，余弦再归一一次。）

#### ③ 余弦太线性，所以要 MLP 打补丁

余弦只能表达「两个向量整体方向一致」；但「配不配」常是**组合条件**
（例如「field 第 3 维偏大 **且** option 第 7 维偏小」），余弦表达不了。

于是 `residual_scorer` 把 4 组 512 维特征拼成 2048 维，交给一个小 MLP：

```python
features = cat([field, option, field * option, abs(field - option)], dim=-1)  # 2048
Linear(2048 -> 512) -> GELU -> Linear(512 -> 1)
```

| 特征 | 作用 |
|---|---|
| `field` | 问题视角 |
| `option` | 选项视角 |
| `field * option` | 逐元素相乘 → **交互/共现** |
| `abs(field - option)` | 逐元素差异 → **哪里对不上** |

后两项是关键 —— 让 MLP 能看见「哪几个维度同时激活」「哪几个维度对不上」。

#### ④ 真实数字

`residual_scorer` 输出 `[1,9,1]`，前 4 个（对应 route 的 4 个选项）：

```text
[-7.78125,  3.8125, -8.3125, -6.25 ]
  account   billing   other   technical
            ^ 只有它是正的大数
```

9 个选项的最终 logits（实测）：

```text
route/account    -3.7722      urgency/0  -3.6958    refund/true   +2.1773
route/billing    +2.2082  ✅   urgency/1  -0.0214    refund/false  -2.9192
route/other      -4.1289      urgency/2  +1.6555 ✅
route/technical  -2.9848
```

**billing 的 3.8125 就是它 logit 冲到 +2.2082 的主要来源。**

#### ⑤ 完整公式（三项合成）

```text
logit = exp(prior_logit_scale) · prior_cos                     ① 词面先验
      + sigmoid(residual_gate) · (                            ② 门控 0~1
            exp(joint_logit_scale) · cos(field, option)        ③ 联合余弦
          + residual_scorer(4 组特征)                          ④ MLP 补丁
        )
```

| 项 | 类比 |
|---|---|
| ① | 简历关键词自动匹配的基线分（不学也知道 billing 和退款相关） |
| ③ | 按整体方向打的分 |
| ④ | 面试官看完整体后手动加减的分（可正可负，能补非线性） |
| ② | 旋钮，训练中学出「③④ 这一整套该信多少」 |

**「打补丁」= 余弦给一个平滑基线，MLP 在基线上加一个可学的修正量。**

### D.12 「6 路投影」的真相：不是 6 维，更不是 `[1,6,512]`

**6 = 6 个独立的 `Linear(2560, 512, bias=False)` 矩阵**，不是 6 个维度、不是 6 个通道。
从头到尾**不存在 `[1, 6, 512]` 这个张量**。

6 个输出的 shape 实测/源码：

| 投影 | 权重 shape | 输出 shape | 输入 |
|---|---|---|---|
| `memory_projection` | `[512, 2560]` | `[1, 370, 512]` | 全部 370 行 |
| `question_projection` | `[512, 2560]` | `[1, 3, 512]` | 3 个问题 span |
| `option_question_projection` | `[512, 2560]` | `[1, 9, 512]` | 问题向量广播 9 份 |
| `global_projection` | `[512, 2560]` | `[1, 512]` | 最后 1 行 |
| `option_context_projection` | `[512, 2560]` | `[1, 9, 512]` | 9 个选项 span |
| `option_lexical_projection` | `[512, 2560]` | `[1, 9, 512]` | 9 个选项词表向量 |

**6 路是「相加」，不是拼接**（`clef.py:429-433`）：

```python
routed = (head.option_context_projection(contexts)          # [1,9,512]
          + head.option_lexical_projection(lexical)         # [1,9,512]
          + head.option_question_projection(owner_questions) # [1,9,512]
         )                                                  # => 仍是 [1,9,512]
```

三个 `[1,9,512]` 逐元素相加，结果**还是 `[1,9,512]`**，不是 1536 维。真实数值（`billing` 位置）：

```text
context   [0.1416, -0.3125, 0.36719, -0.21582]
lexical   [-0.00504, -0.0, -0.00528, -0.00354]
question  [0.24023, -0.71875, -0.29688, 0.20996]
相加      [0.3768, -1.0312, 0.065, -0.0094]
```

另外 2 路加到 field 上（`clef.py:448-453`）：

```python
fields = (base_fields + option_summary_norm(summaries)
          + global_projection(global_vector) + type_embedding(types))  # 全 [1,N,512]
```

#### 「6」的直觉：6 种原料，做成 2 道菜

```text
① memory_projection      -> 「资料库」(K/V)，给后面所有 attention 用
② option_context          -+
③ option_lexical           +-> 相加 => 「9 个选项的查询」(Q)
④ option_question         -+
⑤ question_projection     -+
⑥ global_projection        +-> 相加 => 「N 个问题的 field」
   (+ 选项摘要 + 题型徽章)
```

#### 为什么不能少 / 不能多

**诚实答：6 是架构作者的设计选择，不是数学推导的必然。** 但每个对应一个不可替代的信息源：

| 去掉谁 | 会丢什么 |
|---|---|
| `memory_projection` | 两处 cross-attention 没有 K/V，**整个 head 跑不起来** |
| `question_projection` | 没有 field 基底 |
| `global_projection` | 没有总印象，也做不出 prior 的 anchor |
| `option_context_projection` | 选项在文中的上下文没了 |
| `option_lexical_projection` | 选项字面没了（**但实测激活仅 ±0.005，其他两路 ±0.3 → 训练后几乎没用上**） |
| `option_question_projection` | 选项不知道自己配哪道题，会串题 |

**能少吗？能。** 最明显的就是 `option_lexical` —— 真实数据说明模型基本忽略了它。
但「少」不是删掉就行：权重 shape、参数量、state_dict 全变，**得改架构并从头重训**。
**能多吗？能**（例如加一路「选项在 state 中的出现次数」），同样要改架构 + 重训。
作者选 6，是因为这 6 种信息源覆盖了「全文 / 问题 / 全局 / 选项 ×3 视角」，再加边际收益递减。

> 记法：**「6 路」= 6 个 `[512,2560]` 矩阵 + 6 个不同 shape 的输出 + 逐元素相加。**

### D.13 「让选项和问题互相看」的具体实现（含一个反直觉实测）

#### 机制：标准 QKV attention

```python
# evidence_layers x2：选项 -> 全文
routed, _ = layer.attention(query_norm(queries), memory, memory)
#                           Q=9 个选项      K=V=370 行全文
# layers x4 (TransformerDecoderLayer)：
#   self_attn : Q=K=V=N 个 field
#   cross_attn: Q=N 个 field, K=V=370 行 memory
```

```text
Attention(Q,K,V) = softmax( Q·K^T / sqrt(d_k) ) · V
d_k = width / heads = 512 / 8 = 64
```

#### 真实数字（hook `evidence_layers[0].attention` 手算）

```text
Q = [1, 9, 512]      K = V = [1, 370, 512]
Q·K^T -> [1, 8, 9, 370]   (8 头，每头一张 9x370 相似度表)
softmax 按最后一维 -> 每个选项对 370 个位置各一个权重，每行和 = 1.0000
x V -> [1, 9, 512]
```

3 个 field 之间的 self-attention（8 头平均，实测）：

```text
          route   urgency  refund
route     [0.3325, 0.3263, 0.3411]
urgency   [0.3408, 0.3259, 0.3334]
refund    [0.3057, 0.3231, 0.3713]
```

#### ⚠️ 反直觉：权重几乎是均匀的

```text
均匀分布基准 1/370 = 0.00270，1/3 = 0.33333
account    top1 = 0.0041 (pos 2, token '\n')  行和 = 1.0000
billing    top1 = 0.0040 (pos 225, token '":"')  行和 = 1.0000
other      top1 = 0.0041 (pos 265, token '\n')  行和 = 1.0000
technical  top1 = 0.0045 (pos 362, token 'JO')  行和 = 1.0000
所有选项 top1 都在 0.004~0.005；3x3 也都在 0.30~0.37，接近 1/3
```

**这一层没有形成尖锐的「找证据」聚焦，数学行为更接近「全局平均混合 + 一点可学微调」。**

因此：

1. 之前「9 个调查员各去档案室查资料」是**过度拟人化**的比喻，不宜当作机制理解。
2. **attention 权重 ≠ 可解释性** —— 这次在自己的模型上直接看到了。
3. 只 hook 了 `evidence_layers[0]`（第一层、单条样本），第二层与别的样本可能不同，别过度推广。

**「互相看」落实到机制上就是**：每个位置用自己的 Q 与所有位置的 K 算点积、softmax 成权重、
再对 V 加权求和，于是**每一行的新值都含了所有行的信息**。形状不变（`[1,9,512]` 进/出），
数值被改写 —— 这就是「看」的全部含义。

### D.14 本地 Qwen3.5-4B 是什么精度？**不是 int4**

#### 四层答案

| 层 | 精度 | 证据 |
|---|---|---|
| **磁盘 safetensors** | **bfloat16** | 首个张量 `embed_tokens.weight dtype=torch.bfloat16`；文件合计 **9.32 GB = 4.66B × 2 bytes** |
| **加载进显存（底座线性层）** | **NF4 4-bit + 双重量化** | `_clef_bnb_config`: `bnb_4bit_quant_type="nf4"`, `bnb_4bit_use_double_quant=True` |
| **实际计算** | **反量化回 bf16** | `bnb_4bit_compute_dtype = torch.bfloat16` |
| **决策头 + LoRA** | **fp32** | `head.to(device, dtype=torch.float32)`（`decision.py:761`） |

**NF4（4-bit NormalFloat）不是 int4** —— 针对正态分布权重设计的**非均匀** 4-bit 浮点量化，
比 int4 均匀量化对神经网络权重更准。两个 4-bit 数打包进 1 个 `uint8` 字节存储。

#### 加载后实测 dtype 分布

```text
torch.bfloat16       1,477,149,696
torch.float32           64,785,412
torch.uint8          1,530,920,960
head_dtype         torch.float32
```

| dtype | 含义 |
|---|---|
| `torch.uint8` 1.53B | 4bit 打包后的字节（对应约 3.06B 个 4bit 权重，约 1.53 GB） |
| `torch.bfloat16` 1.48B | 未量化部分（embed_tokens / lm_head / norm / `CLEF_4BIT_SKIP_MODULES` 跳过的模块） |
| `torch.float32` 64.8M | 决策头 32.05M + LoRA 32.46M ≈ 64.5M |

**显存账**：1.53 GB（4bit）+ 2.96 GB（bf16）+ 0.26 GB（fp32 头/LoRA）≈ 4.75 GB，
加激活与缓存 → 实测 **5840 MiB**，吻合。

> 若真是 int4 存储，权重文件应约 2.33 GB，而不是 9.32 GB。

### D.15 logit 公式为什么这么算

```text
logit = exp(prior_logit_scale) · prior_cos
      + sigmoid(residual_gate) · ( exp(joint_logit_scale) · cos(field, option)
                                  + residual_scorer(4 组特征) )
```

#### 训练后三个标量的真实值

```text
prior_logit_scale    = -0.049517
joint_logit_scale    = -0.052002
residual_gate        = 0.001109
sigmoid_gate         = 0.500277
exp_prior_scale      = 0.951689
exp_joint_scale      = 0.949327
```

**三个都几乎停在初值 0 附近**（exp ≈ 0.95 ≈ 1，sigmoid ≈ 0.5）。这不是没训好，
而是设计意图：**随机初始化时就已经是一个合理的打分函数**，训练主要去学 `residual_scorer`
和上游表示，不必先把旋钮从随机值拧到合理位置。

#### 四个设计动机

**① 先验项单独列 = 不用学的底线**

`prior_cos` = 选项字面向量与「问题 + 全局」anchor 的余弦，不训练也知道 `billing` 和「退款」相关。
这是典型的**「结构化先验 + 可学残差」**（与 skip connection 同源）：即使 head 学崩也有一条不差的基线、
给梯度一条短路、第一步就有合理输出，不必从零学「字面匹配」。

**② 门控 `sigmoid(residual_gate)` = 平滑过渡的旋钮**

初值 0 → 0.5，可学到 (0,1)，控制「学到的联合判断」该信多少。
用 sigmoid 而非直接可学权重，是为保证**恒在 (0,1)** —— 先验项永不被完全关掉或反向放大，是数值稳定性护栏。

**③ 两个 scale 用 `exp(...)` —— 最妙的一处**

不只是「保证为正」，而是为了让**温度能精确折进权重**。源码注释（`decision.py:850-852`）：

```python
# logits / T == prior / T + gate * (joint_scale / T * cosine + residual / T)
#             : exact while the rescaled log-scales stay under clamp(max=log 100)
```

因为温度标定是 `logits / T`（除法），而对数尺度是**加法**：

```text
exp(s - log T) = exp(s) / T
```

所以标定后直接减一下、除一下即可（`decision.py:855-866`）：

```python
for name in ("prior_logit_scale", "joint_logit_scale"):
    state[name] = min(float(state[name]), cap) - math.log(temperature)
state["residual_scorer.3.weight"] /= temperature
state["residual_scorer.3.bias"]   /= temperature
```

**收益**：导出模型（GGUF / Cloudflare loader / 合并权重）时**不需要额外带温度文件**，
权重本身已经是「校准后」的。adapter 里的 `folded_temperature = 1.0544` 就是这么来的。
`clamp(max = log 100)` 给折叠留上界，防 `exp` 溢出。

**④ 余弦 + MLP 相加 = 线性基线 + 非线性补丁**

余弦有界 `[-1,1]`、单调、训练稳，但只能表达「整体方向一致」；`residual_scorer` 看 4 组特征
（`field`、`option`、逐元素积、逐元素差），能补「第 3 维大且第 7 维小」这类组合规则。
纯 MLP 要从零学相似度、数据效率低、初期输出乱；先给余弦基线，MLP 只学**修正量**（可正可负），收敛快得多。

真实数字：`billing` 的残差 `+3.8125` 把它推到 logit `+2.2082`，
其他选项是 `-7.78 / -8.31 / -6.25` —— 补丁作用一目了然。

#### 一句话

> **「不用学的字面基线」+「可学的联合判断」，用门控平滑混合，用对数尺度让温度能精确折进权重。**
> 目的：训练稳、初始化即合理、导出时不带额外温度文件。
